# План: «Второй мозг» в Obsidian по методу Карпати (LLM Wiki) на основе CSV агрономических веществ

Источник метода: gist Андрея Карпати "LLM Wiki" (https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)
Данные: f:\downloads\ЦСБ\Complete_Action_Oriented_Agronomic_Substances_CLEANED_v6.csv (275 строк, 10 колонок)
Vault: **F:\agrowiki\Vault** (Obsidian vault = корень проекта; git внутри)
Язык вики: **русский**, названия веществ латиницей (выбор пользователя)

## Ключевая задача (уточнена пользователем)
CSV неполный и неточный. Цель — не просто перенести его в вики, а **по каждому веществу собрать актуальные научные данные и провалидировать информацию**, построив вики как базу валидированных научных карточек с уровнем доказательности и ссылками на источники.

**Фокус (решение пользователя):** в вики входят **все 271 вещество** из CSV, но поиск научной литературы и валидация ограничены **тремя культурами: томат, огурец, клубника**. Для каждого вещества ищем и проверяем эффекты/дозировки именно на этих культурах (если литература по культуре отсутствует — честно помечаем «нет данных по культуре»).

## Суть метода (паттерн LLM Wiki)
- 3 слоя: raw (источники, иммутабельны) → wiki (markdown, пишет и поддерживает LLM) → schema (AGENTS.md — правила для LLM)
- 3 операции: Ingest, Query, Lint (Lint включает закрытие пробелов веб-поиском — в нашем случае это полноценный этап валидации)
- index.md (каталог) + log.md (хронология, append-only, парсится grep-ом)
- Obsidian = IDE, LLM = программист-исследователь, wiki = кодовая база. Человек курирует приоритеты и вопросы.

- **Google Scholar / ScienceDirect** — анти-бот защита; только вручную через Obsidian Web Clipper
- **ci-hub.ru / sci-bot.ru (Sci-Hub зеркала)** — ❌ НЕ используем (пиратские копии, нарушение авторских прав); вместо них: Unpaywall, PMC, DOAJ, OpenAlex OA-ссылки, институциональный доступ пользователя через Web Clipper

Схема валидации источника: PubChem (идентичность) → PubMed/Europe PMC (литература, препринты SRC:PPR) → OpenAlex/Crossref (DOI, OA-копии) → Unpaywall/PMC/DOAJ (полный текст) → web_fetch (доп. контекст). Опционально: EPPO (регуляторный статус), Consensus (score), ChemSpider (хим. детали).

## Валидационная карточка вещества (ядро плана)
Каждая страница вещества содержит:
- **Химическая идентичность**: точное название, CAS-номер, формула/класс
- **Механизм действия** (проверенный, с цитатами)
- **Применение**: способ, дозировки, фазы развития, культуры — с пометкой «проверено исследованиями / только маркетинговые данные»
- **Ожидаемый результат и эффективность** с уровнем доказательности
- **Блок `corrected_dosages` (явные конфликты дозировок)** — таблица: CSV-значение → исправленное → условия (фотопериод/стадия/формуляция) → источник. Пример: CSV «25–200 ppm» → «100 ppm max при длинном дне (>14 ч), PMID:…»
- **Блок `crop_evidence` (по трём культурам)**: для каждой из культур — томат / огурец / клубника — отдельный раздел: найденные дозировки, эффекты, PMID/DOI, пометка «нет данных по культуре», если литературы нет
- **Нормализация дозировок** (`dosage_normalized`): единицы CSV (ppm/mg/L/µM/mM) не сравнимы напрямую — при конфликте конвертировать через молярную массу из PubChem (ppm ≈ mg/L для водных растворов); конверсия записывается в отчёт с указанием источника
- **Привязка к фенофазам (BBCH)**: в статьях искать по ключам BBCH / growth stage / phenological / anthesis / fruit set / veraison; фаза применения в карточке указывается как BBCH-стадия
- **Блок `toxicity_window`**: ED50/TD50/therapeutic index / стойкость в почве — только если литература даёт данные (не выдумывать); при узком окне (Paclobutrazol 75 vs 300 ppm) — предупреждение в карточке
- **PHI и MRL** (обязательно для HIGH-efficacy): PHI (Pre-Harvest Interval), MRL EU/USA/Codex — источники: EU Pesticides Database (efsa.europa.eu), OpenFoodTox (EFSA, машиночитаемо), Codex; иначе null
- **Условия применения** (`application_conditions`): температура, время суток, светочувствительность, влажность (Triacontanol → T>18°C; MeJA летуч при T>25°C; GA3 разлагается на солнце за ~2 ч — вечерняя обработка)
- **Блок валидации** (frontmatter):
  - `validation_status`: unverified → verified / corrected / partial / insufficient_data / conflicting
  - `evidence_level`: strong (обзоры/мета-анализы/множество исследований) / moderate / weak / unverified
  - `last_checked`, `next_review`, `sources` (PMID/DOI/URL), `notes` (что исправлено относительно CSV)
  - опционально: `eppo_code`, `regulatory_status`, `consensus_score`
- Правило: противоречия **не стираются** — фиксируются в `notes` (CSV-значение vs литература)

## 🏗️ Архитектура исполнения: оркестратор и сабагенты

**Оркестратор = главный агент (текущая сессия Copilot).** Роли:
- Держит схему (AGENTS.md) и контекст всей вики
- Ставит задачи поисковым сабагентам, принимает и проверяет их отчёты
- Пишет/обновляет страницы вики, ведёт index.md, log.md, validation.md
- Управляет очередью приоритетов и повторными попытками

**Сабагент поиска (тип research/task, запускается через инструмент task).** Один запуск = одно вещество × 3 культуры:
- Получает **самодостаточный промпт** (сабагенты stateless!): CSV-строку вещества, список API-эндпоинтов (PubMed, Europe PMC SRC:PPR, OpenAlex, Crossref, PubChem), правила лимитов, строгий формат отчёта
- Сам делает API-запросы (curl) с паузами, собирает факты по каждой культуре
- Возвращает **структурированный отчёт (JSON)**: CAS, класс, механизм, по каждой культуре — дозировки/эффекты/PMID/DOI, evidence_level, противоречия с CSV, «нет данных по культуре»

**Принцип «Тонкий агент — Толстый артефакт»** (адаптировано из внешнего плана, согласуется с Карпати):
- Агент не помнит: каждый вызов начинается с чтения артефактов; никакой памяти между вызовами
- Артефакт самодостаточен: файл со всей информацией + provenance (кто, когда, из каких источников)
- Агент делает ОДНО действие и пишет НОВЫЙ артефакт
- Оркестратор не знает домен: только «какая задача → какой агент → какой артефакт»
- Артефакты `raw/evidence/` иммутабельны; wiki-карточки обновляются с сохранением истории (git)

**Артефактный слой** (отчёт сабагента не живёт в чате, а сохраняется в vault):
```
raw/evidence/{код вещества}/
├── search_{code}_{date}.json     ← сырой отчёт сабагента (иммутабелен)
├── facts_{code}.md               ← извлечённые факты (дозировки/условия/статистика)
└── validation_{code}.md          ← отчёт валидации vs CSV (relevance, contraindications)
```
Карточка в wiki/substances/ — обновляемое представление этих артефактов.

**task_queue.md** — очередь задач оркестратора (формат из внешнего плана, адаптирован):
```markdown
## 🔴 HIGH PRIORITY
- [ ] VALIDATE: IBA × tomato  → raw/evidence/IBA/
- [ ] VALIDATE: IBA × cucumber → raw/evidence/IBA/
## 🟡 MEDIUM PRIORITY
- [ ] VALIDATE: GA3 × strawberry (подозрение на конфликт дозировок)
## ✅ COMPLETED
- [x] INGEST: CSV → 271 черновик (дата)
```
Каждый агент обновляет queue, финальный арбитр — оркестратор. Записи в log.md: `## [дата] discover | вещество × культура | N статей`.

**Ключевые правила честности (жёсткие):**
- `verified: true` — только если аннотация реально прочитана; иначе `title_only` или `inferred`
- Нет результатов по культуре → `no_data`, **запрещено** подставлять данные другой культуры
- Никаких выдуманных PMID/DOI/дозировок; если не извлёк — не пишет
- Все неудавшиеся эндпоинты — в `searches.failed` (чтобы оркестратор закрыл пробелы сам)
- **«Нет данных» ≠ «плохо искал»:** если по культуре <5 результатов → fallback-цепочка: (1) запрос без культуры + проверка упоминания культуры в тексте, (2) синонимы культуры (Strawberry → Fragaria × ananassa, Tomato → Solanum lycopersicum, Cucumber → Cucumis sativus); всё ещё 0 → `no_data` с `search_stats` (сколько нашлось всего, сколько упоминают культуру)

**Схема проверки отчётов (4 уровня):**
- **L1. Автопроверка (оркестратор):** JSON валиден по схеме (enum'ы, обязательные поля); каждый PMID батч-запросом esummary (существует, заголовок матчит термины); DOI резолвятся через Crossref; `verified` подтверждается повторно
- **L2. Перекрёстная:** дубли PMID между культурами допустимы, но claims не должны противоречить; найденные противоречия → `conflicts` с severity
- **L3. Человеческий контур:** карточки со статусом `conflicting` и критичными исправлениями → очередь на просмотр пользователем (дашборд «требуют внимания»)
- **L4. Повторная (Lint):** **ежемесячный цикл** — next_review по карточкам, новый поиск публикаций по ключевым веществам (PubMed + Europe PMC SRC:PPR за последний месяц), обновление task_queue.md новыми VALIDATE-задачами

**Fallback-матрица:** если источник у сабагента недоступен (как Europe PMC у iba-search) → оркестратор сам выполняет этот запрос в своей среде (у него источники работают) и дополняет отчёт.

**Лимиты и дисциплина:**
- Параллельность: 5–10 сабагентов за раз (PubMed ≤ 3 запроса/сек без ключа, NCBI банит за превышение)
- Сабагент внутри делает паузы 0.5–1 с между запросами, таймауты, 1 повтор при ошибке
- Оркестратор перепроверяет ключевые PMID через esummary (защита от галлюцинаций сабагента)
- Результат сомнительный → пометка `unverified`, вещество возвращается в очередь

**Механика vs суждение:** механические шаги (271 × 3 запроса, парсинг JSON) можно дополнительно автоматизировать Python-скриптом-воркером (как советует Карпати — «vibe-code скрипт по мере необходимости»), но суждение (сверка с CSV, формулировки, противоречия) остаётся у LLM-оркестратора.

**Расписание:** 1 сессия = пакет 10–20 веществ → 10–20 запусков сабагентов → оркестратор пишет карточки → обновляет трекер. HIGH-приоритет (46 веществ) ≈ 3–5 сессий.
**Будущая оптимизация (не сейчас):** разделение сабагента на Search (механический, заменяемый Python-скриптом) и Analysis (суждение, только LLM) — когда объём оправдает сложность.

### Фаза 1. Схема — AGENTS.md + шаблоны (1–2 часа, итеративно)
- Структура папок, типы страниц, шаблоны frontmatter (включая блок валидации)
- Шкала доказательности, правила нормализации (культуры/классы), правила работы с противоречиями
- Процедуры Ingest / **Validation** / Query / Lint, формат log.md
- Трекер валидации: validation.md (дашборд Dataview по статусам: «проверено», «требуют внимания (conflicting)», «нет данных» + количество claims по каждой культуре) + очередь приоритетов
- **Нормализация синонимов:** перед поиском — PubChem по csv_name → `synonyms` + `iupac_name`; все синонимы включаются в запросы (OR-логика); одинаковый CAS у двух веществ → одна страница с aliases; реестр `raw/normalization/synonyms.json`
- **index.md-иерархия:** index.md = хаб; под-индексы `index_foliar/seed/fruit…`, `index_tomato/cucumber/strawberry`, `index_verified/conflicting/unverified` — каждый через Dataview

### Фаза 2. Bootstrap ingest CSV (2–4 часа, черновой статус)
1. Python-скрипт: CSV → черновики 271 страницы веществ с frontmatter (все `validation_status: unverified`, `aliases_ru`, поля toxicity/PHI-MRL/условий — пустые)
2. LLM по чанкам: восстановить 97 пустых Specific_Action, сгруппировать классы (~20 страниц), создать 8 категорий + механизмы, объединить 8 дубликатов, обратные ссылки
3. Создать 3 страницы культур-хабов (Томат, Огурец, Клубника) с Dataview-списками релевантных веществ (по CSV-поле Target_Crops)
4. index.md, validation.md (очередь из 271), первая запись log.md

### Фаза 2.5. Пилот — 5 веществ (1–2 сессии, перед полным циклом)
Проверка конвейера на выборке, покрывающей все сценарии:
1. **GA3** (клубника) — потенциальный конфликт дозировок (25–200 ppm)
2. **Triacontanol** (клубника) — нюансы формуляции
3. **IBA** (томат) — классический ауксин, много литературы (эталон)
4. **Artemisinin** (томат) — редкое вещество, проверка `insufficient_data`
5. **Chitosan** (3 культуры) — много применений, проверка дубликатов

Цели пилота: проверить JSON-контракт **v1.2** (не нужно ли полей), работу API (не банят ли), парсинг отчётов оркестратором, реальное время на вещество. После пилота — финальная правка контракта и запуск полного цикла.

#### ✅ Результаты пилота (2026-08-04, выполнено)
5 сабагентов (196–466 с), 5 артефактов `raw/evidence/{A,C,G,I,T}/…/search_*_2026-08-04.json`, **L1 пройдена для всех** (IBA 14+14, Triacontanol 10+10, Artemisinin 0+0, GA3 19+18, Chitosan 22+22 PMID+DOI). 7 карточек записаны (вкл. дубли [[Triacontanol (TRIA)]] и [[Chitooligosaccharides]]).

| Вещество | Статус | Evidence | Ключевой вывод |
|---|---|---|---|
| **GA3** | partial | moderate | Механизм усов подтверждён (4 аннотации); ВСЕ дозировки CSV не верифицированы |
| **IBA** | corrected | moderate | CSV 100–1000 ppm замачивание семян на 2–3 порядка выше литературы (0.5 µM–1.5 мг/л, в осн. in vitro) |

| **Chitosan** | partial | strong | Механизм подтверждён 21 аннотацией (~30–66% снижение болезней); CSV-протоколы (400 мг/л ×5, 1–5 кг/га) не верифицированы |

**Дефекты контракта v1.2 → правки для v1.3:**
1. Сабагенты **не пишут файлы** → оркестратор извлекает JSON из ответа (`_scripts/extract_report.py`) и сохраняет артефакт
2. `conflicts` у GA3 содержали **строки вместо dict** (L1 не ловит — добавить type-check в `l1_check.py`)
3. `contraindications` содержали null-заглушки (правило: пустой массив, не placeholder)
4. Для `no_data`-культур claims не имели источников → добавить поле **`related_evidence`** (ближайшие работы по веществу вне культуры)
5. **Europe PMC заблокирован (IPv6) в среде сабагентов** у всех 5 → fallback: оркестратор сам выполняет Europe PMC-запросы (у него работает) и дополняет артефакт
6. Среднее время: ~5 мин/вещество на поиск (не 15–45 мин) → оценка полного цикла понижается

**Уроки для конвейера:** контракт v1.2 рабочий; перед Фазой 3 — внести правки v1.3 в AGENTS.md и l1_check.py; для HIGH-веществ запускать Европейский PMC-повторный запрос оркестратором после сабагента.

### Фаза 3. Валидация и обогащение веществ (ядро работы; реалистичная оценка: 80–120 ч ≈ 30–40 сессий по 2–3 ч ≈ 1–2 месяца при 2–3 сессиях/неделю)
Порядок: **сначала 4 дубликата → HIGH (46) → MEDIUM (146) → LOW (83)**
Рабочий цикл на вещество (пакеты по 10–20 за сессию, ~15–45 мин/вещество):
1. **Поиск по трём культурам**: для каждой культуры (томат, огурец, клубника) отдельный запрос `<вещество> + <культура> + effect/dosage/stress…` в PubMed (2015+, приоритет обзорам/мета-анализам), Europe PMC SRC:PPR (препринты), Crossref, open-access
2. Сбор фактов: CAS, класс, механизм, дозировки, культуры, результаты, противоречия
3. Сверка с CSV: подтвердить / исправить / отметить конфликт (в `notes`)
4. Заполнение блока `crop_evidence` по каждой культуре; если по культуре литературы нет — пометка «нет данных по культуре»
5. Сохранение источников: ссылки PMID/DOI/URL на странице + копии PDF/клипов в raw/sources/<код>/
6. Обновление страницы, status/evidence_level, index.md, log.md, трекера validation.md; добавление обратных ссылок со страниц культур
7. Критерий готовности вещества: status ≠ unverified и ≥1 источник (по любой из трёх культур)

### Фаза 5. Эксплуатация и повторная валидация (постоянно)
- Query: вопросы → синтез с цитатами → ценные ответы складываются в вики
- Ingest новых источников (Obsidian Web Clipper, статьи)
- Lint: сироты, противоречия, устаревшие страницы (next_review), поиск новых публикаций по ключевым веществам

## Риски и решения
- Объём 271 вещество → приоритизация (HIGH первыми) + пакетная работа; ценность появляется после первых 5 сессий
- Недостаток литературы по редким веществам → `insufficient_data` (честный статус вместо выдумки)
- Коммерческие/маркетинговые утверждения в CSV → пометка «unverified», поиск первоисточника
- Платный доступ к статьям → используем бесплатные аннотации PubMed/PMC и open-access
- Устаревание данных → next_review + Lint с поиском новых публикаций
