## 1. Что такое проект

**АгровИки** — Obsidian-вики по методу **Karpathy "LLM Wiki"** (gist 442a6bf555914893e9891c11519de94f):
LLM выступает программистом-исследователем, wiki — кодовая база, Obsidian — IDE, человек курирует.

- **Исходник:** коммерческий CSV — 275 строк, 10 колонок, 267 уникальных кодов веществ
  (стимуляторы, ретарданты, фунгициды, биостимуляторы, гормоны, экстракты, элементы…).
- **Проблема CSV:** неполный, неточный, шумный (89 «химических классов», 97/155 пустых
  Mode_of_Action, 8 кодов продублированы строками с разными дозировками, 146 «грязных»
  Target_Crops). Переносить как есть бессмысленно.
- **Цель:** по каждому веществу собрать актуальные научные данные и **провалидировать**
  CSV-утверждения: что подтверждено, что исправлено, чего в литературе нет.
- **Фокус валидации:** ровно **3 культуры — томат, огурец, клубника**. Нет литературы по
  культуре → честный статус `no_data`. Данные других культур НЕ подставляются.
- **Язык вики:** русский; названия веществ латиницей; библиография англоязычная.
- **Масштаб:** 267 веществ × 3 культуры. Оценка: 80–120 ч ≈ 30–40 сессий по 2–3 ч,
  пакетами 10–20 веществ (5–10 сабагентов параллельно).
- **Прогресс на 2026-08-06:** 11 валидированных карточек из 267 (~4%): 7 partial, 3 corrected,
  1 insufficient_data. Очередь: HIGH 38 / MEDIUM 133 / LOW 83. Стиль-гайд карточек v2.3
  («конечные факты»), 9 категорий применения, smoke-тест конвейера (`smoke_test.py`).

**Кто потребители системы:**
- Человек (Obsidian: чтение карточек, дашборды, ревью конфликтов, скачивание статей);
- LLM-агенты (следующие сессии: читают карточки/артефакты, пишут новые);
- Внешние аудиторы (session_report_*.md по навыку `.github/copilot-skills/session-audit-report/`).

## 2. Философия и инварианты (НЕ ломать при переосмыслении)

1. **Честность — главный принцип.** Никаких выдуманных PMID/DOI/дозировок/цитат. Не извлёк
   из источника — не пиши. «Нет данных» — легитимный статус, а не повод придумать.
2. **Три слоя:** `raw/` (источники, ИММУТАБЕЛЬНЫ) → `wiki/` (контент, пишет LLM) →
   `AGENTS.md` (схема/правила). Служебный слой ВНЕ Obsidian-vault (vault = только контент).
3. **Три операции:** Ingest (приём источников), Query (ответы-синтезы с цитатами),
   Lint (обслуживание: сироты, устаревшее, новые публикации).
4. **Тонкий агент — толстый артефакт.** Сабагенты stateless: прочитал вход → одно действие →
   вернул результат. Артефакт самодостаточен (provenance внутри файла). Памяти между
   вызовами нет.
5. **Иммутабельность артефактов.** `raw/evidence/**/search_*.json` никогда не редактируются.
   Ошибка → новый файл `_rev2.json` с полем `supersedes`. (Правило 11 контракта.)
6. **Противоречия не стираются.** CSV-значение сохраняется, конфликт фиксируется в
   `notes`/`conflicts` с severity (high/medium/low) и источниками.
7. **Доказательность ранжируется:** strong (только рецензированные PMID/DOI) > moderate >
   weak > unverified. Препринты (PPR, bioRxiv и т.п.) НЕ дают strong и помечаются словом «препринт».
8. **verified: true — только если аннотация реально прочитана;** иначе `title_only`/`inferred`.
9. **Культурный фокус жёсткий:** поиск ограничен 3 культурами; <5 результатов → fallback-цепочка
   (запрос без культуры + проверка упоминания, синонимы культуры) → всё ещё 0 → `no_data`
   + `related_evidence` (ближайшие работы вне фокусных культур, чтобы «нет данных» было обосновано).
10. **Единицы:** ppm ≈ mg/L (водные растворы); µM/mM конвертируются через молярную массу
    PubChem с фиксацией источника конверсии; без молярной массы — не сравнивать.
11. **Регуляторика:** PHI (срок ожидания до уборки) и REI (срок выхода на работы) — практический
    блокер для пестицидов; берутся ТОЛЬКО из этикеток препаратов/нац. реестров (e-phy FR,
    BVL DE, EPA, Госреестр РФ). Не найдено → `unknown`. Выдумывать waiting periods ЗАПРЕЩЕНО.
    MRL — справочно, не блокер.
12. **Человек — финальный арбитр** приоритетов, conflicting-карточек и скачивания платных статей.

├── .gitattributes       — EOL-политика: md/json/csv CRLF, py LF (аудит 2026-08-06)
├── raw/                 — CSV, evidence/{A-Z}/<код>/, sources/, normalization/synonyms.json
└── Vault/               — Obsidian vault (только контент)

    ├── raw/             — рабочая папка пользователя: черновики sources (gitignored!)

### 3.1. Модель данных

**Карточка вещества** (`Vault/wiki/substances/<код>.md`, type: substance):
- frontmatter: code, name_en, cas, formula, class, class_family, mechanism, action_category,
  efficacy_csv, validation_status (unverified|verified|corrected|partial|insufficient_data|
  conflicting), evidence_level (strong|moderate|weak|unverified), last_checked, next_review,
  notes[], crops{томат/огурец/клубника: found_verified|found_unverified|no_data}, aliases[],
  aliases_ru[], fallback_status. (Поля-зеркала секций и null-заглушки удалены в v2.2:
  application_csv, sources, toxicity_window, phi_mrl, eppo_code, regulatory_status, consensus_score.)
- Секции: Идентичность → Механизм действия → ⚠️ Валидация CSV-заявок (единая таблица
  «CSV-заявка | Вердикт ✅⚠️❌⚪ | Уточнение | Условия | Severity | Источники») → Научные данные
  по культурам (факты с МЕТОДОМ применения) → ⚠️ Toxicity Window → 📅 PHI и MRL →
  ⚠️ Ограничения и противопоказания (не-CSV) → Источники.
  Секций «Применение (CSV)», «Corrected Dosages», «Противоречия», «crop_evidence» больше НЕТ.

**Артефакт поиска** (`raw/evidence/{A-Z}/<код>/search_*.json`) — JSON по контракту v1.4:
substance, searches (performed/failed/queries_used/fallback_tries), identity (CAS/CID/формула/
синонимы/молярная масса), mode_of_action, crops.{tomato,cucumber,strawberry} (status,
search_stats, claims[]: type/value/context/dosage_normalized/conditions{bbch_stages,…}/
relevance/evidence_quality/stats/sources/quote, gap, related_evidence), toxicity_window,
phi_mrl, contraindications[], conflicts[], verdict, taxonomy_check (class_family_confirmed/
mechanism_confirmed/corrections[]), sources_index.

**Служебные форматы:** log.md (строки `## [дата] операция | …`), task_queue.md
(`- [ ] VALIDATE: <код> × 3 культуры` + секции приоритетов/долгов), frontmatter-конвенции
карточек, synonyms.json (реестр: код → csv_name/name_en/aliases/aliases_ru).

### 3.2. Скрипты конвейера (8 шт., Python, urllib без внешних зависимостей)

| Скрипт | Назначение | Известные недостатки |
|---|---|---|
| `bootstrap.py` | Черновики карточек из CSV; `--dry-run` для проверки; MERGED_CODES SKIP; автозапуск gen_taxonomy | `--full` перезаписывает служебные файлы (опасно); пути захардкожены; перезаписывает unverified-черновики (существовавшие ручные правки теряются) |
| `extract_report.py` | Извлечение JSON из ответа сабагента (raw_decode на каждой `{`), авто-retry до 3 файлов, exit 0/2 | Зависит от того, что сабагент вернёт JSON в финальном сообщении |
| `l1_check.py` | L1: схема v1.4 + type-check + taxonomy_check + supersedes + PMID esummary + DOI Crossref | Нет unit-тестов |
| `fallback_europepmc.py` | Europe PMC SRC:PPR запросы оркестратором (у сабагентов IPv6-блок) | Только для одного вещества за запуск |
| `gen_taxonomy.py` | 9 категорий/29 семейств/15 механизмов; OVERRIDES, FAMILY_OVERRIDES, `--refresh`; шаблон категорий — `contains(action_category, …)` (мульти-категории) | Маппинг в коде, а не в данных |
| `gen_synonyms.py` | synonyms.json из aliases карточек | Перезапись вручную после каждой валидации |
| `digest.py` | Компактный дайджест отчётов | Редко используется |
| `smoke_test.py` | Целостность после массовых операций: дубли кодов, запрещённые поля, старые секции/баннеры у валидированных, таксономия у всех (exit 0 = ок) | Нет unit-тестов для отдельных функций |

### 3.3. Конвейер валидации (ядро работы)

```
CSV-строка + текущая таксономия карточки
  → research-сабагент (stateless, контракт v1.4, 3 культуры за запуск)
  → JSON в финальном сообщении → extract_report.py → raw/evidence/.../search_*.json
  → (Europe PMC недоступен у сабагента? → fallback_europepmc.py оркестратором)
  → L1 (схема+PMID+DOI) → L2 (перекрёстные противоречия) → L3 (человек: conflicting)
  → карточка (frontmatter + секции по стиль-гайду v2.3) + taxonomy_check.corrections
  → task_queue.md / validation.md / Vault/index.md / log.md / synonyms.json
  → smoke_test.py (целостность) → git commit + push
```

4 уровня проверки: **L1** автопроверка схемы/PMID/DOI · **L2** перекрёстная непротиворечивость ·
**L3** человек (conflicting, критические исправления) · **L4** повторная (Lint, next_review,
новые публикации, миграции контракта).

## 4. Подводные камни (эмпирика — самое ценное для брейншторма)

### 4.1. Сабагенты и контракт
- **2 из 5 сабагентов возвращают пустой/незавершённый ответ.** Не блокер: авто-retry до 2
  попыток (extract_report exit 2 → RETRY в task_queue), после 2 неудач → карточка
  `insufficient_data` с gap-описанием.
- Сабагенты **выдумывают PMID/DOI/дозировки** при нехватке данных — L1 (esummary/Crossref)
  единственная защита; `verified: true` только при реально прочитанной аннотации.
- **Europe PMC заблокирован (IPv6) в среде сабагентов**, у оркестратора работает → fallback.
- Сабагент возвращает JSON текстом (иногда обёрнут в ```json, иногда с хвостом) →
  `extract_report.py` ищет JSON raw_decode на каждой `{`.
- Контракт эволюционировал v1.2 → v1.3 → v1.4 (по итогам пилотов и 3 аудитов): добавлялись
  `related_evidence`, `taxonomy_check`, `supersedes`, жёсткие типы (`conflicts`/`contraindications`
  — массивы объектов, НЕ null/строки). Часть пилотных карточек на старом контракте → долг
  **MIGRATE v1.2→v1.4**.

### 4.2. Данные и таксономия
- 8 кодов CSV дублируются строками (разные категории/дозы одного вещества) → объединение в
  одну карточку: claims в «Применение (CSV)», обе дозировки в application_csv, коды в aliases.
  После объединения коды-спутники не имеют карточек (MERGED_CODES в скриптах).
- 89 CSV-классов → 29 семейств — маппинг шумный, требует ручных OVERRIDES (гербициды
  замаскированы под «Synthetic auxin», PHMG под «Polymeric guanidine» → PGR и т.п.).
- 97/155 пустых Specific_Action → восстанавливать из Mode_of_Action.
- 77 веществ получили mechanism «по дефолту семейства» — на аудит (AUDIT_TAXONOMY).
- CAS-совпадение у разных кодов → объединять страницы (MeJA = Methyl Jasmonate, TRIA = Triacontanol).

### 4.3. Регуляторика и литература
- PHI/REI в открытых БД (EUPD/PPDB/Codex) отсутствуют → только этикетки/нац. реестры, ручной
  сбор человеком (очередь `raw/sources/papers_to_fetch.md`). EUPD/Codex — JS-приложения, API нет.
- Препринты (SRC:PPR) НЕ strong; DOI препринтов проходят Crossref-проверку, но помечаются.
- Культурные синонимы обязательны в fallback-запросах (Fragaria × ananassa, Solanum lycopersicum…).

### 4.4. Инженерные грабли
- **EOL:** репозиторий CRLF для md/json/csv, LF для py (`.gitattributes`, аудит 2026-08-06);
  но edit-инструменты и Obsidian периодически пишут LF → «фантомные» diff; regex `^...$`
  съедал `\r` при `--refresh` (исправлено). Правило: писать файлы Python-ом с явной
  кодировкой/EOL, после массовых правок — нормализация + `smoke_test.py`.
- **Консоль cp1252:** вывод кириллицы — кракозябры (косметика), но Add-Content в log.md
  записал ANSI и потерял символы — журнал дописывать только Python-ом.
- **Регрессия bootstrap (2026-08-06):** проверочный запуск без `--dry-run` пересоздал
  объединённые карточки (MeJA/TRIA) и стёр таксономию у 256 черновиков → защита:
  `--dry-run`, MERGED_CODES SKIP, автозапуск gen_taxonomy, `smoke_test.py`.
- **Dataview-категории:** `action_category = "X"` не работал для мульти-категорий
  (Chitosan: 3 значения) → `contains(action_category, "X")` во всех страницах (2026-08-06).
- Пути захардкожены (`f:\agrowiki\...`) — скрипты не переносимы.
- Нет unit-тестов (кроме smoke_test); L1-проверки менялись вручную под новые правила.
- Синхронизация дашбордов (validation.md ↔ Vault/index.md) — ручная, легко рассинхронизировать.
- Dataview не рендерится ВНЕ vault (validation.md в корне — «мёртвый» дашборд, живой — index.md).
- Obsidian-плагины: workspace/graph/community-plugins.json — в .gitignore (community-plugins
  оставлен в git), коды плагинов переустанавливаются.
- Дубли страниц возникали при переименованиях/объединениях (MeJA draft) и остатки
  шаблонов после миграции (двойной «## Источники» у Glycine Betaine) — ловится smoke-тестом.
- Терминология: акарициды ≠ митициды (рус. термин — акарициды, от Acari; митицид — англ. калька).

## 5. Что работает хорошо (сохранить в спецификациях)

1. **Иммутабельные артефакты с provenance** — позволили 3 цикла аудита без потери данных.
2. **L1-автопроверка** (схема + type-check + PMID esummary + DOI Crossref) — ловит галлюцинации.
3. **Пакетная обработка:** 5 сабагентов параллельно за сессию → 5–10 карточек.
4. **Fallback Europe PMC оркестратором** — закрывает IPv6-блок сабагентов.
5. **Таксономия как данные + OVERRIDES** — гибкость при сохранении идемпотентности
   (скрипт повторно запускается без порчи ручных правок).
6. **Русские алиасы** (aliases_ru) — поиск по-русски в Obsidian работает, граф не ломается.
7. **Реструктуризация:** служебный слой вне vault — Obsidian Graph/Cmd+O не засоряется.
8. **Внешние аудиты каждые N коммитов** — контракт и правила эволюционируют осознанно.
9. **Честные статусы** (`no_data`, `insufficient_data`, `unknown` для PHI) — доверие к базе.
10. **Стиль-гайд v2.3 «карточка = конечные факты»** — единая таблица валидации CSV-заявок,
    секции без процесса поиска; 11/11 валидированных карточек мигрированы.
11. **smoke_test.py** — целостность конвейера после массовых операций (exit 0 = ок).
12. **EOL-политика `.gitattributes`** — CRLF/LF разведены по типам файлов.

## 8. Формат OpenSpec (краткая справка)

OpenSpec — практика SDD: спецификации — живые документы в репозитории, изменения проходят
через **change proposals** (брейншторм → обоснование → задачи), спорные решения фиксируются
в **ADR**. Типовая структура каталога `openspec/` (уточнить по официальной документации
Fission-AI/OpenSpec и CLI `openspec` при старте):

```
openspec/
├── projects/            — описание продуктов/компонентов
├── changes/             — change proposals (по одному каталогу на изменение)
│   └── <id>/proposal.md — rationale / outcome / impact / tasks
├── specs/               — спецификации компонентов (capabilities)
└── ADRs/                — архитектурные решения
```

Рекомендации для сессии:
- Каждый change proposal — атомарный, с явным «почему» (ссылка на боль из раздела 6 или
  вопрос из раздела 7). Не смешивать «как есть» и «как должно быть».
- Спецификации писать на уровне **инвариантов и контрактов** (что система обещает), а не
  деталей реализации; детали — в ADR.
- Русский язык допустим, но технические термины и идентификаторы — латиницей.
- Фиксировать НЕ-цели (что система сознательно НЕ делает: например, не валидирует культуры
  вне 3 фокусных, не выдумывает PHI, не использует пиратские источники).

## 9. Процедура для LLM-сессии (как работать с этим документом)

1. Прочитать первоисточники (раздел 11), особенно `log.md` — это хронология решений и
   их причин, лучший источник эмпирики.
2. Собрать инвентарь болей (раздел 6) → превратить в change proposals.
3. Провести брейншторм открытых вопросов (раздел 7) → решения зафиксировать в ADR.
4. Спецификации писать по компонентам: (а) данные и контракты, (б) конвейер валидации,
   (в) таксономия и нормализация, (г) Obsidian-представление, (д) операции (Ingest/Query/Lint),
   (е) качество и проверки L1–L4, (ж) человек в цикле, (з) миграция, (и) инфраструктура.
5. Валидировать спеки на ретроспективе: каждая спека должна объяснять, какой подводный
   камень из раздела 4 она закрывает.
6. Выход: `openspec/` + короткий отчёт «спеки → какие боли закрывают» + список открытых
   вопросов для человека.

## 10. Словарь терминов

- **Карточка** — страница вещества в wiki (frontmatter + секции).
- **Артефакт** — файл фактов из поиска (`search_*.json`, `orchestrator_fallback_*.json`).
- **Сабагент** — stateless research-агент, возвращающий JSON по контракту.
- **Оркестратор** — главный агент сессии: извлекает артефакты, гоняет L1, пишет карточки.
- **L1–L4** — уровни проверки (автосхема/PMID/DOI → перекрёстная → человек → Lint).
- **Научные данные по культурам** (бывш. crop_evidence) — секция карточки с доказательствами
  по культурам, каждый факт с МЕТОДОМ применения (in vitro/полевой/биотест…).
- **Валидация CSV-заявок** (бывш. Corrected Dosages + Противоречия) — единая таблица
  «CSV-заявка → вердикт ✅⚠️❌⚪ → уточнение → условия → severity → источники»;
  одна CSV-заявка = одна строка; вердикты CSV — только в этой таблице.
- **PHI/REI/MRL** — срок ожидания до уборки / срок выхода на работы / максимальный остаток.
- **BBCH** — шкала фенофаз (BBCH 61 = 10% цветков открыто, BBCH 73 = зелёная ягода).
- **PPR** — препринт (bioRxiv/medRxiv/Research Square и т.п.), не strong-доказательство.
- **SRC:PPR** — фильтр Europe PMC для препринтов.
- **Vibecode** — разработка без явных спецификаций, итеративным промптингом (как сделан проект сейчас).
- **SHELF_LIFE** — категория «Хранение и лёжкость» (9-я, вне CSV, расширение схемы 2026-08-06).
- **Стиль-гайд v2.3** — текущий стандарт карточек (конечные факты, без баннеров/процесса поиска).
